# Plano: Login Social via OIDC (apps/api, apps/web)

## Contexto

Os botões Github e Gmail existem na tela de Login e Cadastro desde o mockup original, mas nunca fizeram nada além de `console.info` (ver `plan/PaginaLogin.md`). O plano de Secure by Design (`plan/SecureByDesign.md`) desabilitou os botões (`disabled`, sem handler) em vez de deixá-los simular uma funcionalidade que não existe, e apontou para este arquivo como o desenho de como implementá-los de verdade.

Este é **só o desenho** — nenhuma linha de código daqui foi implementada. Ele existe para ser avaliado e, quando aprovado, executado como os outros planos do projeto.

## Nota de implementação (2026-10-08)

Implementado (`apps/api/src/auth/oidc/`, `apps/web/src/pages/LinkAccountPage/`), com os seguintes ajustes de escopo em relação ao desenho acima:

- **`WEB_APP_ORIGIN` (novo env var).** O desenho dizia "redireciona para `/perfil` no front" como se fosse um path relativo — mas a API e o front são origens diferentes, então um redirect relativo do callback navegaria dentro da própria origem da API, não do SPA. O callback (e a vinculação) agora redirecionam para `${WEB_APP_ORIGIN}/perfil` (ou `/vincular-conta`), um env var fixo por ambiente, mesma lógica de `API_ORIGIN`.
- **`API_ORIGIN`/`WEB_APP_ORIGIN`/credenciais OIDC não são obrigatórios em produção.** `OIDC_LINKING_TOKEN_SECRET` continua obrigatório (é um segredo barato de gerar e um default incorreto é risco real de forjar vinculação). Os demais não: OIDC é um método de login opcional sobre o de senha, e uma implantação que não queira configurar Google/Microsoft ainda precisa subir normalmente — sem esses vars, os botões sociais simplesmente falham no provedor.
- **Vinculação automática quando a conta existente não tem senha local — só com `email_verified`.** O desenho só cobria "conta local com senha" vs. "conta nova". Faltava o caso de uma conta já criada via OIDC (sem `passwordHash`) logar com um *segundo* provedor usando o mesmo email: como não há senha local para proteger, a nova identidade é vinculada automaticamente **desde que o `id_token` traga `email_verified: true`**. Ver a nota de correção abaixo — a primeira versão disso não checava essa claim e era um account takeover.
- **`oidc_flow` carrega seu próprio `exp`**, checado no servidor — não só o `Max-Age` do cookie, que só controla se o *navegador* ainda manda o cookie, não se o servidor aceitaria um state "velho" por algum outro motivo.
- Gap do front (`socialProviders.ts` com `github`/`google`→`Gmail`) corrigido para `google`/`microsoft`.
- Testes e2e usam um IdP falso local (`apps/api/test/oidc-fake-idp.ts`) para cobrir o checklist da seção 5 sem depender de credenciais reais do Google/Microsoft.
- ~~`linking_token` é limpo mesmo numa senha errada~~ — revertido na rodada 2 de correção abaixo: uma senha errada agora permite tentar de novo, igual ao login normal.

## Nota de correção pós-revisão (2026-10-08)

O PR #19 abriu com a nota de implementação acima e passou em todos os checks de CI (incluindo `e2e-web`/Lighthouse). A revisão automática (`claude` GitHub Action) encontrou um **bloqueante real** na vinculação automática introduzida acima, que foi corrigido antes de considerar o escopo fechado:

- **🔴 Bloqueante — `email_verified` não era validado.** Sem essa checagem, o passo "vinculação automática quando a conta existente não tem senha local" era exatamente o formato do ataque **nOAuth**: um provedor que deixa o usuário definir um email arbitrário e não verificado na própria conta (algumas configurações de tenant Microsoft Entra ID permitem isso) seria suficiente para assumir qualquer conta só-OIDC com esse mesmo email — sem senha, sem prova nenhuma. Corrigido: `OidcIdentityClaims` agora carrega `emailVerified`, e `resolveIdentity` só auto-vincula quando `emailVerified === true`; caso contrário, falha com 401 genérico (não há senha para cair no fluxo de `/vincular-conta`, então a única opção segura é recusar). O caminho "conta local **com** senha" nunca precisou dessa checagem — a senha já é a prova.
- **🟠 `name`/`email` do provedor sem limite de tamanho.** Um `name` > 100 chars ou `email` > 254 chars (larguras das colunas no `schema.prisma`) chegava ao Prisma como erro bruto (500). Corrigido: `email` > 254 rejeita (401 genérico, mesma mensagem dos outros claims inválidos); `name` é truncado em 100 chars.
- **🟠 Callback mostrava JSON bruto na origem da API, inclusive quando o usuário só cancela no provedor.** `?error=access_denied` (ou qualquer `?error=`) agora redireciona para `${WEB_APP_ORIGIN}/login` em vez de lançar uma exceção — é tráfego normal, não uma tentativa de ataque. As outras rejeições (state/PKCE/assinatura/`aud` inválidos) continuam como erro JSON: são anômalas por natureza, nenhum usuário real as atinge seguindo os redirects normalmente.
- **🟠 `docker-compose.yml` usava `CORS_ORIGINS` (lista) como `WEB_APP_ORIGIN` (precisa ser uma origem só) e deixava `OIDC_LINKING_TOKEN_SECRET` vazio por padrão**, quebrando o `docker compose up api web` existente com uma causa pouco óbvia. Corrigido: `WEB_APP_ORIGIN` ganhou var própria, e `OIDC_LINKING_TOKEN_SECRET` agora falha com a mesma mensagem clara de `JWT_SECRET` (`:?...`) em vez de deixar o container crash-loopar.
- **🟡 `LinkAccountDto.password` sem `@MaxLength`** num endpoint público e rate-limited que roda `scrypt` — adicionado `@MinLength(8)`/`@MaxLength(72)`, mesmas bordas de `CreateUserDto`.
- **🟡 Botões sociais continuavam habilitados mesmo sem `*_CLIENT_ID`**, redirecionando com `client_id=` vazio. `/start` agora responde `404` quando o provedor não está configurado.
- **🟡 `VincularContaPage` fugia do Atomic Design** (formulário inline em vez de organism) **e do nome em inglês** que `LoginPage`/`SignUpPage`/`ProfilePage` usam. Corrigido: formulário extraído para `components/organisms/LinkAccountForm/`, página renomeada para `LinkAccountPage` (a rota `/vincular-conta` e o texto em tela continuam em pt-BR, só o nome do componente mudou).
- Testes novos para cada um dos pontos acima (unitários + e2e), incluindo o cenário completo de account takeover que o bloqueante permitia (criado e then provado fechado).

**Não corrigido nesta rodada** (apontado pela revisão, mas de menor severidade/maior escopo — ver a rodada 2 abaixo, que revisitou e corrigiu dois destes três):
- ~~Duplicação de leitura de env entre `env.ts` e `oidc.constants.ts`~~ — corrigido na rodada 2.
- Checagem cruzada `tid`/`iss` para Microsoft (defesa em profundidade adicional, não necessária com o fix de `email_verified` — ainda adiada).
- ~~Conflito de `createFromOidc`/`linkProviderIdentity` por corrida real entre duas requisições simultâneas~~ — `createFromOidc` corrigido na rodada 2 (`linkProviderIdentity` já mapeava para 409 desde a rodada 1).

## Nota de correção pós-revisão, rodada 2 (2026-10-08)

A rodada 1 acima corrigiu o bloqueante na **vinculação automática**, mas a mesma revisão automática, numa segunda passada sobre o commit da correção, encontrou que a checagem de `email_verified` faltava num segundo lugar: a **criação de conta nova**. Mais um bloqueante real, mais alguns importantes:

- **🔴 Bloqueante — conta nova também sem `email_verified` (ataque de pré-registro).** Sem essa checagem, um atacante com um provedor que aceita email arbitrário podia criar uma conta com o email da vítima **antes** dela se cadastrar. Quando a vítima depois entrasse de verdade via Google (email verificado), o auto-link da rodada 1 juntaria a identidade real dela à conta plantada pelo atacante — mesma classe de account takeover, só que pela porta da criação em vez da vinculação. Corrigido: a checagem de `emailVerified` em `resolveIdentity` agora cobre os dois ramos (criação de conta nova **e** auto-link), não só o segundo; o ramo "conta local com senha" continua sem precisar dela (a senha já protege).
- **🟠 `/vincular-conta` não aceitava nova tentativa após senha errada.** A rodada 1 documentou isso como leitura literal do desenho ("sucesso ou falha"), mas a revisão (duas vezes, em rodadas diferentes) apontou que isso é mais rígido que o login por senha normal sem motivo de segurança real — `LOGIN_THROTTLE` já limita quantas tentativas, e o próprio `exp` do `linking_token` já limita por quanto tempo. Corrigido: `OidcController.link` só limpa o cookie **depois** de um sucesso; uma senha errada permite tentar de novo com o mesmo `linking_token`, dentro da validade dele.
- **🟠 Callback ainda mostrava JSON bruto para falhas que um usuário legítimo pode encontrar** (ex: Microsoft sem `email_verified`, ou o fluxo expirado por demorar demais). A rodada 1 só tratou `?error=` do provedor. Corrigido: `OidcController.callback` agora captura toda `HttpException` que `OidcService.authenticate` lança e redireciona para `/login` em vez de deixar vazar como JSON — qualquer erro que **não** seja uma `HttpException` (um bug de verdade, não uma rejeição prevista) continua propagando para o `AllExceptionsFilter`, que loga e devolve 500 normalmente, em vez de mascarar silenciosamente uma falha real como "tente de novo".
- **🟠 `POST /auth/oidc/link` podia devolver 409 sem isso estar documentado/testado.** Adicionado `@ApiConflictResponse` e um teste cobrindo o conflito (`UsersService.createFromOidc`/`linkProviderIdentity` mapeando `P2002` para `ConflictException`).
- **🟡 Corrida em `createFromOidc`:** duas chamadas simultâneas para o mesmo email novo podiam ambas passar o `findByEmail` antes de qualquer `create` terminar; a perdedora batia num `P2002` não tratado (500 bruto). Corrigido com o mesmo padrão de `UsersService.create`/`linkProviderIdentity` — mapeia para `ConflictException`, que agora também vira redirect para `/login` (ver ponto acima).
- **🟡 `env.ts` lia e validava variáveis OIDC que nada consumia** (`oidc.constants.ts` já lê `process.env` direto, com seus próprios defaults). Isso tinha deixado de ser só "duplicação estilística" quando a rodada 1 removeu a obrigatoriedade em produção desses vars — sem efeito de validação, eram só código morto. Removido de `env.ts`: `apiOrigin`, `webAppOrigin`, `googleClientId`, `googleClientSecret`, `microsoftClientId`, `microsoftClientSecret`. `oidcLinkingTokenSecret` continua lá — é o único que ainda tem um efeito real (a obrigatoriedade em produção).
- Testes novos para cada ponto acima (incluindo o cenário completo de pré-registro: o atacante tenta primeiro, falha, e o dono real da conta consegue criar a própria conta normalmente depois).

**Não corrigido, deliberadamente adiado** (ambas as rodadas): checagem cruzada `tid`/`iss` para Microsoft. Defesa em profundidade adicional — não necessária para fechar o account takeover, que já está coberto por `email_verified` nos dois ramos.

## Nota de correção pós-revisão, rodada 3 (2026-10-08)

Uma terceira passada da revisão automática sobre o commit da rodada 2 não encontrou mais bloqueantes de segurança — a vulnerabilidade de account takeover (rodadas 1 e 2) está fechada. Os três pontos que a própria revisão marcou como "merecem ajuste antes do merge" eram de correção/UX/robustez, não bypass de segurança:

- **🟠 Microsoft não emite `email_verified` de forma confiável** (o endpoint v2.0 da Entra ID simplesmente não garante essa claim) — na prática, isso faria o cadastro novo e o auto-link via Microsoft falharem sempre, sobrando só a vinculação por senha como caminho funcional. Corrigido: `OidcService.verifyIdToken` agora aceita `xms_edov` (a claim que a própria Microsoft recomenda para esse cenário — "externally-set domain ownership verified") como alternativa a `email_verified`. Documentado aqui: para o Microsoft funcionar além da vinculação por senha, o **App Registration no Entra ID precisa pedir `xms_edov` como optional claim** — isso é configuração de infraestrutura, não algo que o código force.
- **🟠 Falha no callback redirecionava para `/login` sem nenhuma mensagem (WCAG 3.3.1).** Corrigido: o redirect agora é `/login?oidcError=1` — um código genérico, nunca dizendo qual checagem falhou — e `LoginPage` lê esse parâmetro e mostra um `FormError` genérico ("Não foi possível entrar com o provedor. Tente novamente."), removendo o parâmetro da URL depois (`useEffect` + `setSearchParams` com `replace: true`, para não deixar o erro reaparecer num refresh).
- **🟠 `API_ORIGIN`/`WEB_APP_ORIGIN` sem validação em produção** podiam cair silenciosamente em `localhost` mesmo com credenciais OIDC configuradas. Corrigido: `env.ts` agora exige os dois, mas só **quando** `GOOGLE_CLIENT_ID` ou `MICROSOFT_CLIENT_ID` está configurado em produção — continuam totalmente opcionais numa implantação que não usa OIDC.
- **🟡 Query do Prisma em `findByProviderIdentity` usava `user.findFirst` com filtro de relação** em vez de buscar direto pela chave única composta. Corrigido: `oidcIdentity.findUnique({ where: { provider_providerSub: {...} } })`.
- **🟡 Tipagem: `findByProviderIdentity`/`createFromOidc` diziam devolver `StoredUser`** (com `passwordHash: string | null`), mas o `omit` global do Prisma faz `passwordHash` vir `undefined` em tempo de execução nesses dois casos — nenhum código lê esse campo hoje, mas o tipo mentia. Corrigido: tipados como `Omit<StoredUser, 'passwordHash'>`.
- **🟡 Comentário em `schema.prisma` impreciso sobre o que a constraint garante** (dizia "um por provedor por usuário", mas o `@@unique([provider, providerSub])` garante só que uma identidade externa não é reclamada por dois usuários — nada impede um usuário ter duas identidades do mesmo provedor). Corrigido o texto.
- Teste novo faltante: email não verificado + conta local **com** senha → ainda oferece `/vincular-conta` normalmente (prova que esse ramo é seguro independente da claim, como os comentários já afirmavam).
- `apps/web/public/robots.txt` ganhou `Disallow: /vincular-conta` e a entrada correspondente saiu do `llms.txt` — é uma página transitória do fluxo, não conteúdo que vale indexar ou divulgar a crawlers de LLM. (Ajuste na rodada 4 abaixo: isso quebrou o Lighthouse CI, não ficou em `e2e/routes.ts` como esta nota dizia originalmente.)

**Não corrigido, deliberadamente não feito** (duplicação entre `env.ts`/`oidc.constants.ts` para `OIDC_LINKING_TOKEN_SECRET`): é o mesmo padrão que `JWT_SECRET` já usa neste projeto (`auth.constants.ts` tem seu próprio `getJwtSecret()` com o mesmo `DEV_SECRET` duplicado) — `env.ts` só agrega a validação de boot, cada módulo de domínio lê o valor que de fato usa. Não é uma inconsistência nova introduzida por este PR.

## Nota de correção pós-revisão, rodada 4 (2026-10-08)

A correção de SEO da rodada 3 (`Disallow: /vincular-conta` no `robots.txt`) quebrou o próprio CI: o Lighthouse pontua uma rota bloqueada por `robots.txt` **e** listada em `e2e/routes.ts` como falha de SEO (`categories.seo` caiu para 0.63, abaixo do `minScore: 1` que `CLAUDE.md`/`lighthouserc.cjs` exigem). O projeto já tinha esse padrão resolvido para `/perfil` e `/posts/novo` — ambas **ausentes** de `e2e/routes.ts` justamente por serem privadas/não-indexáveis. Corrigido: `/vincular-conta` saiu de `e2e/routes.ts` também; a cobertura de a11y continua garantida no nível de componente (`LinkAccountPage.test.tsx` já roda `expectNoA11yViolations`), só não tem mais a suíte Playwright de página inteira.

Uma quarta passada da revisão automática, já sem achar nenhum outro bypass de segurança, levantou dois pontos reais de robustez/deploy:

- **`linking_token` forçado em `SameSite=Lax`, quebrando deploys cross-site.** O cookie é setado pelo redirect do callback mas lido de volta num XHR `POST /auth/oidc/link` disparado pela página `/vincular-conta` — isso é um request same-origin-com-a-API, não uma navegação de topo. Se API e front estiverem em domínios registráveis diferentes (`COOKIE_SAMESITE=none`, o cenário cross-site que `security-standards.md` já trata como "segunda opção"), esse XHR é cross-site do ponto de vista do cookie, e `SameSite=Lax` nunca é enviado nele — a vinculação sempre falharia com 401 "token ausente" nesse deploy, sem nenhum teste pegar isso (localhost e o docker-compose são sempre same-site). `oidc_flow` genuinamente precisa de `Lax` (sobrevive ao redirect de topo vindo do provedor); `linking_token` não — ele não passa por nenhuma navegação cross-site, só por um XHR que precisa respeitar o `COOKIE_SAMESITE` configurado, igual ao cookie de sessão. Corrigido: `getLinkingTokenCookieOptions()` agora usa `baseCookieOptions()` (configurável) em vez de forçar `'lax'`; a limpeza do cookie passou a usar o `getClearCookieOptions()` genérico (também configurável) em vez do limpador específico de `oidc_flow`, que ficou renomeado para `getClearOidcFlowCookieOptions()` para não sugerir que serve para os dois.
- **Nada impedia `OIDC_LINKING_TOKEN_SECRET` de repetir `JWT_SECRET`/`CSRF_SECRET`.** O comentário já dizia que isso nunca deveria acontecer (motivo: isolar o alcance de um vazamento), mas `env.ts` não checava. Corrigido: comparação direta contra os dois no boot, com erro agregado como os demais.
- Testes novos para os dois pontos (incluindo a asserção e2e do `linking_token`, que dizia `SameSite=Lax` e passou a dizer `SameSite=Strict`, o default de `COOKIE_SAMESITE` em teste).

**Detalhes menores apontados e deliberadamente não corrigidos nessa rodada** (a própria revisão os marcou como não-bloqueantes): `LINKING_TOKEN_TTL_MS` coincide em valor com `OIDC_COOKIE_MAX_AGE_MS` sem compartilhar a constante; `parseOidcProvider` ecoa o valor de `:provider` da URL na mensagem de erro; abrir o fluxo em duas abas sobrescreve o único `oidc_flow` e a primeira aba cai em `?oidcError=1` (comportamento aceitável, só documentado aqui). O teste de replay do `linking_token` foi adicionado na rodada 5 abaixo.

## Nota de correção pós-revisão, rodada 5 (2026-10-08)

Uma quinta passada da revisão automática — já sobre um commit sem nenhum bypass de segurança nas rodadas anteriores — confirmou isso explicitamente ("nenhum problema bloqueante encontrado") e recomendou três ajustes antes do merge, todos de robustez/correção, não de segurança:

- **`fetch` ao `token_endpoint` sem timeout.** Um provedor lento (ou que nunca responde) prenderia o callback — e o cookie `oidc_flow` que ele está validando — indefinidamente. Corrigido: `AbortSignal.timeout(10_000)` na chamada; o `catch` que já tratava falha de rede cobre o abort da mesma forma (mesmo erro genérico, sem distinguir).
- **`sub` sem limite de tamanho**, ao contrário de `email`/`name` — um valor acima de 255 chars (a largura de `OidcIdentity.providerSub` no schema) chegaria a um `create` do Prisma como erro bruto (500) em vez do redirect genérico para `/login?oidcError=1`. Corrigido com a mesma checagem que `email`/`name` já tinham.
- **Cookie `linking_token` não era limpo num 409** (identidade já vinculada — replay do token ou corrida). Como esse token específico nunca vai ter sucesso numa segunda tentativa (a identidade já está vinculada), mantê-lo não oferece nenhuma retentativa útil, só um beco sem saída até expirar sozinho. Corrigido: `OidcController.link` agora limpa o cookie tanto no sucesso quanto no 409 — continua preservando o cookie só na falha de senha (que é genuinamente retentável, ver rodada 2). Adicionado também o teste e2e que faltava: replay do `linking_token` depois de uma vinculação bem-sucedida → 409.

**Observações menores, sem bloqueio** (a própria revisão as marcou assim — deliberadamente não corrigidas): checagem cruzada `tid`/`iss` para Microsoft multi-tenant (mesma defesa em profundidade adiada desde a rodada 2); o segredo de dev `'dev-only-linking-secret-change-me'` duplicado entre `env.ts` e `oidc.constants.ts` (mesmo padrão de `JWT_SECRET`, ver rodada 3); a interpolação `${OIDC_LINKING_TOKEN_SECRET:?...}` no `docker-compose.yml` é avaliada para o arquivo todo, então até `pnpm db:up` (que só sobe o Postgres) passa a exigir essa variável no `.env` raiz depois de atualizar a branch — mesmo padrão que `JWT_SECRET` já tinha, não uma regressão nova; o redirect para `/vincular-conta` (inclusive para um email não verificado de um tenant Entra qualquer) já revela que aquele email tem conta local, mas `POST /users` devolvendo 409 "Email já cadastrado" já fazia exatamente essa mesma revelação antes deste PR — enumeração de email é um problema pré-existente, não uma regressão.

## Nota de correção pós-revisão, rodada 6 (2026-10-08)

Uma sexta passada, de novo sem nenhum bypass de segurança, encontrou um bug funcional real (o próprio texto da revisão: "nada bloqueante do ponto de vista de segurança. O item 1 é um bug funcional que eu corrigiria antes do merge") e uma inconsistência de UX que valia resolver junto:

## 1. Fluxo (Authorization Code + PKCE)

A API nunca vê a senha do usuário no provedor — esse é o ponto do OIDC. O fluxo:

**Limitação conhecida (aceita, não é um bug):** há só um `oidc_flow` por navegador — se a pessoa abrir o login social em duas abas, ou escolher um segundo provedor antes de terminar o primeiro, a segunda `/start` sobrescreve o cookie da primeira, e a aba antiga cai em `oidcError=1` ao concluir. Comportamento cru, mas sem risco de segurança (cada cookie ainda é validado contra o seu próprio `state`); a pessoa só precisa tentar de novo na aba que falhou.

1. `GET /auth/oidc/:provider/start` (`:provider` = `google` | `microsoft`, validado estritamente — qualquer outro valor é `400`, não cai num provedor default nem tenta montar uma URL a partir dele —, `@Public()`, `@NoCsrf()` — é GET). Gera `state` (CSRF do próprio fluxo OAuth, aleatório, `httpOnly`) e um par PKCE (`code_verifier` aleatório + `code_challenge = base64url(sha256(code_verifier))`), guarda os dois num cookie `httpOnly`, `SameSite=Lax` de vida curta (5 min — precisa sobreviver ao redirect cross-site de volta do provedor, por isso não pode ser `Strict`), e redireciona (`302`) para o `authorization_endpoint` do provedor com `response_type=code`, `code_challenge`, `code_challenge_method=S256`, `state`, `scope=openid email profile`, `redirect_uri` apontando para o callback abaixo.
2. Usuário autentica no provedor (fora da nossa API inteiramente).
3. Provedor redireciona para `GET /auth/oidc/:provider/callback?code=...&state=...`. A API:
   - Valida que o `state` da query bate com o do cookie usando `timingSafeEqual` (rejeita CSRF do próprio fluxo OAuth e ataques de tempo na comparação) e que não expirou.
   - Troca o `code` pelo token no `token_endpoint`, mandando o `code_verifier` do cookie (prova de posse do PKCE — fecha o "authorization code interception attack").
   - Valida o `id_token` recebido: assinatura via JWKS do provedor (`jwks_uri` do discovery document, cacheado — o cache por si só já limita quantas vezes a API bate no `jwks_uri`, mas a estratégia de cache escolhida precisa também limitar refetch forçado por `kid` desconhecido/inválido, senão um atacante pode mandar `id_token`s com `kid` lixo só para forçar a API a martelar o endpoint do provedor —, nunca `alg: none` nem HS256 — só os algoritmos RS256/ES256 que o provedor realmente usa), `iss`, `aud` (= nosso `client_id`), `exp`, `iat`/`nbf` com clock skew tolerável de 1–2 min (relógio do servidor nunca é perfeito), `nonce` se usado.
   - Extrai `email` (normalizado, minúsculo) e `sub` (id estável do provedor) das claims.
   - `findOrCreateByProviderIdentity(provider, sub, email)`: se já existe um `User` com esse `(provider, providerSub)`, usa esse usuário. Senão, se existe um `User` com esse email criado via senha local, **não funde automaticamente** — ver "Vinculação de conta" abaixo. Senão, cria um novo `User`.
   - A partir daqui é o fluxo de login normal: assina o JWT da sessão, seta `access_token` + `csrf_token`, redireciona (`302`) para `/perfil` no front.
4. Limpa os cookies de `state`/`code_verifier` no callback, sucesso ou falha.

## 2. Redirect URI: a superfície de ataque real

Um `redirect_uri` não validado é o jeito mais comum de quebrar OIDC na prática (abre um "open redirect" que vaza o `code`). Regras:

- `redirect_uri` enviado ao provedor é **sempre** o mesmo valor fixo, hardcoded por ambiente (`${API_ORIGIN}/auth/oidc/:provider/callback`), nunca construído a partir de um parâmetro da requisição.
- Esse valor precisa estar na allowlist de redirect URIs cadastrada no Google Cloud Console / Entra ID App Registration — o provedor rejeita qualquer valor fora dela, mas isso é defesa em profundidade, não a única barreira.
- Nenhum parâmetro tipo `?returnTo=` ou `?next=` neste fluxo: ao contrário de um app que aceita um destino pós-login arbitrário, aqui o destino pós-login é sempre `/perfil`, fixo.

## 3. Modelo de dados

```prisma
model User {
  id             Int       @id @default(autoincrement())
  name           String    @db.VarChar(100)
  email          String    @unique @db.VarChar(254)
  passwordHash   String?   @map("password_hash") // opcional: usuário só-OIDC não tem senha local
  createdAt      DateTime  @default(now()) @map("created_at")
  identities     OidcIdentity[]
}

model OidcIdentity {
  id         Int      @id @default(autoincrement())
  provider   String   @db.VarChar(20) // "google" | "microsoft"
  providerSub String  @map("provider_sub") @db.VarChar(255) // claim `sub`, estável
  userId     Int      @map("user_id")
  user       User     @relation(fields: [userId], references: [id])
  createdAt  DateTime @default(now()) @map("created_at")

  @@unique([provider, providerSub])
  @@map("oidc_identities")
}
```

`passwordHash` vira opcional (`String?`) — um usuário que só já logou via OIDC não tem senha local. `AuthService.signIn` (login por senha) já trata `!user` como 401; passa a tratar `!user.passwordHash` da mesma forma (mesma mensagem genérica, para não revelar "essa conta só existe via Google").

## 4. Vinculação de conta (o caso que exige uma decisão do usuário)

Se alguém loga com Google usando `maria@exemplo.com`, e já existe uma conta local com esse mesmo email (senha), **a API não funde as duas automaticamente** — fazer isso sem prova de posse da conta local seria deixar qualquer um "assumir" uma conta existente só por controlar aquele email no Google. Em vez disso:

- O callback detecta o email já cadastrado sem uma `OidcIdentity` correspondente.
- Gera um `linking_token` de curtíssima duração (3–5 min, uso único — invalidado após a primeira tentativa de uso, sucesso ou falha), assinado (HMAC com segredo próprio, nunca o mesmo segredo do JWT de sessão) e contendo só `email`, `provider`, `providerSub` e `exp`.
- Guarda esse `linking_token` num cookie `httpOnly`, `SameSite=Lax`, de vida curta — **nunca em query string**: query param vaza em histórico do navegador, no header `Referer` de requisições subsequentes e em logs de acesso de proxy/CDN, e esse token prova posse de uma identidade OIDC, então vazamento dele é tão sensível quanto vazar o próprio `code`. Redireciona (`302`) para `/vincular-conta` no front sem nenhum parâmetro sensível na URL.
- `/vincular-conta` (front) pede a senha atual da conta local e faz `POST /auth/oidc/link` (API) com a senha no corpo; a API lê o `linking_token` do cookie (não do body, não da query), valida assinatura e expiração, valida a senha (via `verifyPassword`, igual ao login normal) e só então cria o `OidcIdentity` vinculando as duas contas. Limpa o cookie do `linking_token` ao final, sucesso ou falha.

Isso é a parte do fluxo com mais superfície de erro de segurança (account takeover via vinculação indevida) — vale uma revisão própria quando for implementada, não só seguir este desenho ao pé da letra.

## 5. Segurança — checklist

- [x] PKCE obrigatório (`code_challenge_method=S256`), nunca o fluxo implícito.
- [x] `state` aleatório (`crypto.randomBytes`), de uso único, expira em minutos, comparado com `timingSafeEqual`.
- [x] `:provider` validado estritamente contra `['google', 'microsoft']` — qualquer outro valor é `400` antes de tocar em qualquer config de OIDC.
- [x] `redirect_uri` fixo por ambiente, nunca parametrizável pela requisição.
- [x] `id_token` validado via JWKS (biblioteca, não parsing manual) — assinatura, `iss`, `aud`, `exp`, `iat`/`nbf` com clock skew de 1–2 min.
- [x] Cache de JWKS limita refetch forçado por `kid` desconhecido (não deixa um `id_token` malicioso forçar a API a bater repetidamente no `jwks_uri` do provedor).
- [x] Nenhuma claim do provedor entra no JWT da nossa sessão além de `sub`/`email` (mesma regra que já vale hoje — ver `auth/auth.types.ts`).
- [x] Login por senha em conta `passwordHash = null` (só-OIDC) retorna o mesmo 401 genérico do login por senha incorreta — não revela que a conta existe só via OIDC.
- [x] Vinculação de conta exige prova de posse (senha atual) quando a conta tem senha local; quando não tem (conta só-OIDC) **ou quando cria uma conta nova**, exige `email_verified: true` do provedor em vez de confiar no email sozinho (ver as duas notas de correção pós-revisão — tanto a vinculação automática quanto a criação de conta nova, incondicionais, foram bloqueantes encontrados em rodadas separadas). `linking_token` é assinado, de uso único, expira em minutos, e viaja só em cookie `httpOnly` — nunca em query string.
- [x] Segredos do cliente OIDC (`client_secret` de cada provedor, segredo de assinatura do `linking_token`) são env vars (`GOOGLE_CLIENT_SECRET`, `MICROSOFT_CLIENT_SECRET`), validados em `src/env.ts` como os outros segredos — nunca hardcoded, nunca logados.
- [x] Rate limiting no `/auth/oidc/:provider/start`, `/callback` e `/auth/oidc/link`, mesma lógica de `LOGIN_THROTTLE`.
- [x] Testes e2e cobrindo: `state` inválido/ausente/expirado → rejeita; `code_verifier` que não bate com o `code_challenge` → rejeita; `id_token` com assinatura inválida → rejeita; `id_token` de um `aud` diferente → rejeita; login por senha numa conta só-OIDC → 401 genérico; criação de usuário novo via OIDC de ponta a ponta; email já existente bloqueia fusão automática e só vincula após senha correta em `/auth/oidc/link` (`apps/api/test/oidc.e2e-spec.ts`, 20 casos, com um IdP falso local).

## Nota de correção pós-revisão, rodada 13 (2026-10-09)

Nenhum achado de segurança novo, mas a revisão encontrou dois bloqueantes reais de robustez de uma vez (a primeira desde a 1-2 com mais de um ponto que não é repetição):

- **🔴 Corrigido — `/auth/login` e `POST /auth/oidc/link` tinham buckets de throttle separados para a mesma senha.** Os dois verificam a senha da mesma conta local (`verifyUserPassword`), mas `ThrottlerGuard` chaveia por `(classe, handler, IP)` por padrão — então cada rota tinha seu próprio `LOGIN_THROTTLE` (5/min), somando 10 tentativas/min contra uma única conta, não 5. Obter um `linking_token` para tentar contra `/link` não custa nada ao atacante: ele é emitido para qualquer email no ramo de colisão com senha, independente de `email_verified` (de propósito — a senha já é a prova nesse ramo). Corrigido com `LoginThrottlerGuard` (`common/login-throttler.guard.ts`), uma subclasse de `ThrottlerGuard` que sobrescreve `generateKey` para dar a mesma chave a `AuthController.login` e `OidcController.link`, substituindo o `ThrottlerGuard` puro como `APP_GUARD` global em `app.module.ts` — não dava para simplesmente empilhar um guard por rota (`@UseGuards`), porque isso teria rodado o guard duas vezes por requisição e dobrado a contagem (mesma razão já documentada nos comentários de `AuthController`/`UsersController`). Teste novo: `login-throttler.guard.spec.ts` (unidade, prova que as duas rotas colidem na mesma chave e que toda outra rota continua isolada) e um caso em `throttle.e2e-spec.ts` (intercala tentativas entre as duas rotas e confirma que o 429 chega no total combinado, não em `2×limit`).
- **🔴 Corrigido — issuer do Google rejeitava uma forma documentada.** Igual ao que a rodada 12 já tinha corrigido para essa mesma claim — ver a nota daquela rodada; esta rodada apenas confirmou que a correção ficou certa.
- Também corrigidos nesta rodada: `@ApiForbiddenResponse` (CSRF) faltando em `POST /auth/oidc/link` no Swagger (`oidc.controller.ts`); o callback de sucesso não limpava um `linking_token` esquecido de uma tentativa de vinculação abandonada antes de montar a nova sessão — nit de higiene, sem risco (o token é de uso único e vinculado a uma tentativa específica, mas não havia razão para deixá-lo até expirar por conta própria).

**Considerado e explicitamente recusado:** nenhum item novo esta rodada — os repetidos de sempre (segredo de dev duplicado, `tid`×`iss` da Microsoft) não vieram de novo no resumo desta passada.
